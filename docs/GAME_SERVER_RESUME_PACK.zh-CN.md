## 二、可直接粘贴的简历项目块（推荐）

### 高并发在线服务后端（流式推送 + 异步任务调度）· 个人项目

**2025.06 – 2026.08** | Go / TypeScript / Node.js / PostgreSQL / Redis  
可线上演示

独立设计并实现面向真实用户的在线服务后端，覆盖服务端流式推送、近似最近邻检索、异步任务调度与可观测性；以延迟分位数、并发正确性、故障降级与任务调度为核心目标，能力可迁移至游戏服务器中的会话服务与后台任务系统。

- 设计检索链路：查询向量化 → ANN 索引 Top-K → 规则重排序；知识库约 **5.5k** 向量，生产检索 **p50 约 78ms**（目标 &lt;200ms），并对 p99 尖刺做上游网络 RTT 与索引耗时拆解
- 实现基于 SSE 的服务端流式推送；完成 **5 路并发长连接读流 0 失败**；将端到端延迟拆为检索与下游模型首包，定位瓶颈在外部模型调用而非自身检索层
- 设计 **Go 异步 Worker**：可插拔向量化接口、批量处理（batch=32）、失败不写脏数据；基于消息队列消费组、按租户串行、租约超时回收与可控延迟压测矩阵，验证多副本扩展性
- 可靠性：上游依赖多级降级；事务外可靠入队（Outbox）+ 幂等写入；结构化调用日志记录延迟与各阶段耗时，支撑排障
- 工程化：网关与业务服务可同进程或拆分为独立 HTTP 服务；配套压测报告与设计文档

**技术栈：** Go、TypeScript、Node.js、PostgreSQL、向量检索（HNSW）、SSE、Redis Streams、HTTP

## 三、约 250 字网申描述

独立完成在线辅导后端的核心服务层，覆盖流式对话、向量检索与异步任务调度。基于 PostgreSQL + pgvector（HNSW）实现相似度检索与重排序，生产环境检索延迟 p50 约 78ms，并对 p50/p99 做瓶颈拆解。基于 SSE 实现服务端流式推送，完成多路并发稳定性验证。针对长耗时导入任务，设计 Go Worker 异步平面（批处理、租约、幂等与 Mock 压测矩阵），避免在 Serverless 请求内阻塞。配套调用日志与多级降级策略，保证上游 API 抖动时服务仍可用。项目强调延迟治理、并发正确性与工程可演进，与游戏服务器中的会话推送、后台任务、稳定性保障能力同构。

## 五、高频追问 · 对照 JD 的答法

### Q1. 你没做过游戏服，为什么投这个岗？
游戏服本质是：**有状态/半状态服务 + 高并发连接 + 稳定与性能**。我用学习产品练了流式推送、分位数延迟、异步 Worker 与降级；语言上 Go 已用于 Worker 平面。业务规则可以入职后学，工程肌肉我已经在练。

### Q2. 高并发你怎么证明？
诚实分层：  
- **已测：** 本地 5 路 SSE 并发 0 错误；RAG 生产采样 p50/p99。  
- **已设计/骨架：** Go Worker 多实例、Redis Streams、per-couple 串行、Mock 压测矩阵。  
不要说「已支撑百万在线」。可说「按游戏服思路做了调度与压测框架，当前业务量级小，重点在正确性与可扩展结构」。

### Q3. 为什么用 Go？和 C++ 比？
异步 Worker、多副本抢任务、部署简单，Go 更合适快速落地。若团队主栈 C++，核心是协议/并发模型/内存与延迟意识，语言可迁移；我也可以补课 C++ 基础题。

### Q4. 分布式里最难的点？
至少一次投递下的**幂等**（importId+idx）、租约超时回收防双写、以及 **per-tenant 串行 vs 全局吞吐** 的公平性。用 Mock 延迟才能暴露调度瓶颈，而不是一直卡在外部 API。

### Q5. 和帧同步/状态同步有什么关系？
本项目没有帧同步。可类比：SSE 是单向状态推送；游戏里可能是 UDP/TCP 自定义协议。我展示的是**推送与一致性/幂等思维**，不是宣称做过帧同步。

### Q6. AI 工具怎么用的？（加分项）
用 Cursor/Agent 做实现加速，但 SLA、压测数字、降级策略和架构取舍是自己定的；用 OpenSpec 把需求写成可验收规格，避免 AI 乱改范围。
